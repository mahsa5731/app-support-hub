# Programmer Analyst 2 job alignment

AppSupportHub is a portfolio exercise designed to demonstrate transferable
engineering practices. It is not evidence of work performed for the City of
Winnipeg or any other employer.

| Job capability | Planned AppSupportHub evidence | Planned phase | Honest limitation |
| --- | --- | --- | --- |
| Implementing and supporting commercial and custom applications | Phase 02 models commercial/custom systems, ownership, criticality, lifecycle, and five maintainable custom-application use cases; UI and operations follow later | 2, 4, 7 | A portfolio simulation cannot reproduce the scale, vendors, or operational pressures of a live enterprise estate. |
| Maintaining, enhancing, troubleshooting, and optimizing applications | Phase 02 models incident, enhancement, and change-request workflows; diagnostics, logging, and measured query review remain planned | 2, 4, 7 | No production users or service-level commitments are represented. |
| Gathering requirements and producing specifications | Identified requirements, acceptance criteria, change assessments, ADRs, and traceability documentation | 1, 5, ongoing | Requirements are project-defined rather than elicited from actual City stakeholders. |
| Feasibility, impact, and risk analysis | Structured business need, technical impact, security impact, risk, test plan, and rollback plan | 5 | Assessments use portfolio scenarios, not employer changes. |
| Applying cybersecurity practices | Server-side validation, identity, role-based authorization, rate limiting, secure configuration, auditing, and security tests | 6 | The project is not a security certification or a substitute for an organizational security program. |
| Working with relational databases | PostgreSQL schema, constraints, migrations, transactions, pagination, and standard SQL reporting | 3, 7 | PostgreSQL and standard SQL demonstrate relational database skills; they do not constitute Oracle PL/SQL experience. |
| Manual and automated testing | Phase 02 adds deterministic Domain/Application unit tests and expands architecture tests; integration, security, deployment, and manual acceptance tests remain planned | 1–8 | Test scenarios use synthetic portfolio data and do not prove production reliability. |
| Understanding architecture and the software development life cycle | Modular-monolith boundaries, ADRs, phased delivery plan, quality gates, CI/CD, and final audit | 1, 8, 9 | Documentation demonstrates applied understanding within one project, not ownership of an enterprise-wide SDLC. |
| Collaborating with technical specialists, coordinators, users, and stakeholders | Role-aware assignment, acceptance criteria, change history, review checkpoints, and stakeholder-oriented documentation | 4–8 | Collaboration is modelled in the product and documents; no claim is made of City stakeholder participation. |
| Working in a mixed .NET, PowerBuilder, PL/SQL, and Classic ASP environment | .NET implementation plus a bounded CSV-import demonstration for data exported by a hypothetical legacy application | 1, 5 | The project implements .NET only. The CSV boundary demonstrates integration design and does not constitute PowerBuilder, Classic ASP, Oracle, or PL/SQL development. |
