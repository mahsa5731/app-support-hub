# Programmer Analyst 2 job alignment

AppSupportHub is a portfolio exercise designed to demonstrate transferable
engineering practices. It is not evidence of work performed for the City of
Winnipeg or any other employer.

| Job capability | Planned AppSupportHub evidence | Planned phase | Honest limitation |
| --- | --- | --- | --- |
| Implementing and supporting commercial and custom applications | Phase 04 delivers maintainable Razor and REST catalog workflows for commercial/custom systems, including bounded search, metadata, ownership, vendor, and confirmed lifecycle changes | 2, 4, 7 | A portfolio simulation cannot reproduce the scale, vendors, or operational pressures of a live enterprise estate. |
| Maintaining, enhancing, troubleshooting, and optimizing applications | Phase 04 delivers filtered support queues, overdue text, joined detail/history, and explicit detail, assignment, priority, due-date, and status actions; diagnostics and measured query review remain planned | 2, 4, 7 | No production users or service-level commitments are represented. |
| Gathering requirements and producing specifications | Requirements trace to implemented page/API routes, error policy, manual journeys, OpenAPI, and ADRs; change-assessment specifications follow in Phase 05 | 1, 4, 5, ongoing | Requirements are project-defined rather than elicited from actual City stakeholders. |
| Feasibility, impact, and risk analysis | Structured business need, technical impact, security impact, risk, test plan, and rollback plan | 5 | Assessments use portfolio scenarios, not employer changes. |
| Applying cybersecurity practices | Server-side validation, identity, role-based authorization, rate limiting, secure configuration, auditing, and security tests | 6 | The project is not a security certification or a substitute for an organizational security program. |
| Working with relational databases | Phase 03 implements PostgreSQL tables, named constraints, indexes, foreign keys, migrations, transactions, stable history, and optimistic concurrency; pagination and reporting remain planned | 3, 7 | PostgreSQL and standard SQL demonstrate relational database skills; they do not constitute Oracle PL/SQL experience. |
| Manual and automated testing | Deterministic Domain/Application tests, architecture enforcement, real PostgreSQL HTTP integration tests, antiforgery/PRG journeys, accessibility assertions, and a Phase 04 manual script | 1–8 | Test scenarios use synthetic portfolio data and do not prove production reliability or WCAG conformance. |
| Understanding architecture and the software development life cycle | Modular-monolith boundaries, ADRs, phased delivery plan, quality gates, CI/CD, and final audit | 1, 8, 9 | Documentation demonstrates applied understanding within one project, not ownership of an enterprise-wide SDLC. |
| Collaborating with technical specialists, coordinators, users, and stakeholders | Support-team ownership, assignee workflows, immutable actor-labelled history, review checkpoints, and stakeholder-oriented manual/API documentation | 4–8 | Collaboration is modelled in the product and documents; no claim is made of City stakeholder participation. |
| Working in a mixed .NET, PowerBuilder, PL/SQL, and Classic ASP environment | .NET implementation plus a bounded CSV-import demonstration for data exported by a hypothetical legacy application | 1, 5 | The project implements .NET only. The CSV boundary demonstrates integration design and does not constitute PowerBuilder, Classic ASP, Oracle, or PL/SQL development. |
